## 第二轮优化（同日）：卡进行中 + 刷新/进查看页卡死

### 根因
1. **刷新面板/进查看页卡死**：面板刷新 → `checkLogin()` → `/panel/api/login/check` → `_probe_login_state()` 慢路径会用**采集进程正占用的同一个 browser_profile 再 launch 一个 Chromium**（profile 锁冲突 → 无限等待，launch 无超时）；且 `_login_probe_lock` 让后续所有接口排队；前端 fetch 也无超时 → 彻底卡死。
2. **采集卡进行中**：浏览器端 `fetch()` 无 AbortController、Python 侧 `page.evaluate` 无超时 → 某个媒体/CDN 请求永久挂起 → 整个采集进程卡住 → 状态永远 running。

### 修复
**`app/backend/control_panel.py`**
- `_probe_login_state`：采集/发现运行中直接返回 unknown（不再启动浏览器，避免 profile 锁冲突）；慢路径整体包 `asyncio.wait_for(..., 20s)`（原来只有 goto 有 8s 超时，launch 无超时）
- `login_cookie_import`：采集/发现运行中跳过浏览器验证，直接写 `data/cookies_backup.json`（下次采集 launch 时生效），返回 deferred 标记
- `_run_scrape` 看门狗：改为每 30s 轮询 `proc.returncode` + 检查日志 mtime，连续 10 分钟无日志输出 → `proc.kill()`；不用 `wait_for(proc.wait())`（反复取消/重等 Future 有竞态）
- 前端 `panel.html`：全局 fetch 拦截器加 60s 统一超时（AbortController），杜绝无限转圈

**`app/extractor/web_scraper.py`**
- 所有网络 evaluate 加硬超时 + JS fetch 加 30s AbortController：
  - `_api_fetch_all_messages` 的 fetchBatch evaluate → `wait_for(120s)`
  - `_fetch_batch`（媒体批量下载）→ `wait_for(60s)` + JS 端每个 URL 30s abort
  - 用户头像/会话头像下载 → `wait_for(40s)` + 30s abort
  - `_resolve_sender_identities` → `wait_for(40s)` + 30s abort
- `extract_all` 单会话兜底超时：`wait_for(self._extract_conversation(...), 25min)`，超时打印后继续下一个会话

**`app/common/db.py`**
- `connect()` 加 `timeout=30` + `PRAGMA busy_timeout=30000`：采集进程写库时，查看页/面板读请求等待而非立即抛 "database is locked"

### 验证
- 看门狗逻辑用模拟脚本验证（持续输出不杀 / 无输出超时杀）
- 全部 Python/JS 语法通过

## 第六轮（同日）：卡在"重新加载聊天页面"（short_id 捕获优化）

### 根因
`_steal_short_id_from_sdk` 是"清 SDK 缓存 → 整页重载 → 重新点击会话 → 拦截 SDK
请求偷 short_id"，每个单聊会话都要经历一次页面重载（慢且脆弱，曾卡在重新加载）。

### 优化（`app/extractor/web_scraper.py`）
**点击会话前就装请求拦截器**（pre_capture）：
1. `_extract_conversation` 在 `_find_and_click_conversation` 之前安装 request 拦截器
2. 点击后 SDK 首次拉消息的 get_by_conversation 请求直接被拦截 → 8s 内捕获 short_id
3. 捕获成功 → 完全跳过"清缓存+重载"流程（绝大多数情况）
4. 8s 未捕获 → 回退到原 `_acquire_short_id`（重载兜底，带 30s 超时）
5. 群聊（conv_id.isdigit()）不等待捕获，直接用 conv_id 当 short_id

### 效果
- 单聊会话获取 short_id 从"重载页面 5-30s+" 降到"点击后 1-2s 内"
- 大幅降低页面重载失败/卡住的概率

1. `stop_scrape` / `refresh_stop` 只 `proc.terminate()` 杀 extract.py 主进程——

1. 新增 `_kill_process_tree(proc)`：Windows 用 `taskkill /F /T /PID` 递归杀整个
   进程树（含 Chromium），失败回退 proc.kill()
2. `stop_scrape` / `refresh_stop`：改用 `_kill_process_tree` + 设 stopped 标记

## 第十一轮（同日）：真实复现 + 根治"服务卡死"

### 关键突破：真实运行复现
用 start.bat 启动服务 + 真实采集"都"会话（13322 条历史）完整复现问题：
1. **short_id 捕获已生效**（点击后 1-2s 直接捕获，不再重载）
2. 会话列表扫描 64 个（多遍扫描生效）
3. 消息抓取正常（batch 进度 200+ msg/s）
4. **但服务在 batch #6 后无响应**——所有接口超时，CLOSE_WAIT 堆积

### 根因（服务卡死）
**`_run_scrape`/`_run_discover` 用 asyncio 管道逐行读取子进程输出**：Windows
ProactorEventLoop 上 `asyncio.wait_for(proc.stdout.readline(), timeout=30)` 反复
超时取消 readline 会损坏 IOCP 管道状态 → 事件循环被阻塞 → 整个 uvicorn 无响应
（所有接口超时、连接 CLOSE_WAIT 堆积）→ 用户只能反复重启服务。

### 修复（`control_panel.py`）
